## 一、为什么要退回（不是文笔问题，是固定句式）

原文样本（照录，未改一字）：

```
s3_123928d2 《玉楼春·东风又作》卡2 [结构抓手]

s3_040abf01 《琐寒窗·暗柳啼鸦》卡2 [结构抓手]
```

**为什么机械项查不出**：SPEC 对 memory 卡只有「单卡 55–100 字」和词表约束。
「同一句换个说法再写一遍」正好能把 `d` 凑到 55 字下限——缺陷正好是判据的填充手段。

## 二、缺陷的精确形态（这决定了整改怎么做）

对 41 张卡做结构统计：

| 观测项 | 读数 |
|---|---|
| 落在「该诗**最后一张**卡」 | **40/41 = 97.6%** |
| 卡类型是【结构抓手】 | **40/41 = 97.6%** |
| 句对类型：完全相同 / 近重复（只删虚词） | **31 / 12** |
| 命中卡当前字数 | **47–60 字**（下限 55） |
| **删掉重复句后的字数** | **9–44 字 → 41/41 张全部跌破 55 字下限** |

**⇒ 结论：光删句一定不合格。每张卡必须「删掉重复句 + 补一句真正的新信息」。**

这是本任务书最重要的一条：**整改不是删字，是补内容。**

---

## 三、整改规则（五条硬性）

1. **删掉被判定重复的那一句**（清单里 `hits[].s2` 给出原文，逐字匹配）。
2. **补写一句新的**，位置放回原处，读起来仍通顺。新句必须满足：
   - **承载清单里该诗没有出现过的信息**（另一处诗眼、另一段的结构功能、另一个意象的走向）；
   - **不是对已删句或相邻句的同义改写**——判据会自动抓，同义改写仍会命中；
   - 指向**这首诗的具体内容**，不能是「情景交融」「意境深远」这类可套任何诗的评语。
3. **改完单卡 55–100 字**（非空白字符数，含标点）。
4. **改完该诗 memory 卡合计 130–260 字**，条数仍为 2–3 条，`t` 仍取受控词表四值。
5. **整卡读一遍：三个信息点必须互不相同。** 本批还有一个附带问题——
   删掉重复句后剩下的句子常常仍在同一个意思上打转（例：`s3_123928d2` 剩下三句全是「倒计时」）。
   遇到这种，**重写整张卡**，不要只换一句。

## 六、验收标准（灵玉复检口径，与本任务书同源）

全部满足才算通过：

2. 41 张卡逐张人工读：**三个信息点互不相同**，且新句指向本诗具体内容（不是通用评语）；
3. 单卡 55–100 字、合计 130–260 字、条数 2–3，**0 处越界**；
4. 引文双口径失配 **0**；禁 markdown / 套话 **0**；
5. **未命中的 124 张卡（165−41）零变化**（逐字节 diff）；
6. `串讲` 字段零变化；`id`/顺序/category/level 零变化；
7. `index.html` **零改动**。首选判据（无歧义）：`git rev-parse HEAD:index.html` 仍为 `53fb72f22ea1d64359af3910a2505e9fdbf4cd33`，且 `git status --porcelain -- index.html` 为空。
   若要用 POEMS 段 sha256 做二次确认，**切法必须写死**（2026-11-01 补，起因见下）：

   ```python
   import hashlib, re
   b = open('index.html', 'rb').read()
   s = re.search(rb'const POEMS\s*=\s*\[', b).start()   # 锚点：const POEMS 四个字起
   print(hashlib.sha256(b[s:]).hexdigest())            # 切到文件末尾 EOF
   ```
   该切法下期望值 = `0802270ca99e9631f506d3fbc20082ee`。

   > **为什么补这段**：原任务书只给了 hash、没给切法。trae 按「数组本体 `[..]`」切，
   > 得到 `920859342da9705f47a1bc7bd2d3109b`，与本条对不上，于是如实报了「基准漂移」并停下。
   > 两个值都对，错在任务书没定口径——**裸 hash 不是判据，hash + 切法才是**。
   > 今后写这类条款一律用「git blob hash」或「脚本 + 期望值」成对给，不要只给一个 hex。


任一项不满足 → 退回重改，不进合入队列。
