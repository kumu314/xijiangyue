# 三端一致 + 7523 首「935 同等待遇」工作量估算（2026-11-17，灵玉）

## 0. 一句话答案

按当前实测差距，字面意义的「7523 首全部拿到 935 首同等深度」不是一个提交，而是一条内容量产线：还差 **40,445 行逐句白话译文**（分母：真值源 7523 首共 47,896 行，其中 7,451 行已有 m；缺口 40,445 = 新增 6588 首的 40,406 行 + 935 首自身的 39 行待裁定）和 **6588 篇串讲扩写**（分母：真值源中不属于网页版 935 首的 6588 首，串讲全部低于 120 字；935 首里 612/935 = 65.5% 达到 200 字以上）。工程侧的「三端同源」本身只有约 1–2 人日 + 人类在云控制台的导入/配置动作，前提是枯木先批 commit/push 和云端写入。

## 1. 依赖前提（未验证项显式列出）

- 已验证（本轮实跑，命令见 §6）：网页版 `index.html` 工作区 4,464,205 字节，其中 POEMS 数组 1,378,860 字符；`poems_new.json` 7523 首、压缩 JSON 11,242,745 字节；两者 id 交集 935/935，网页版 935 首全部在真值源内，真值源多出 6588 首。
- 已验证：真值源基础字段齐全率见 §2；飞花令派生索引 `feihuaData` 49 个关键字、71,710 条句子，当前由 935 首派生。
- 已验证：云库导入素材已生成 76 个分片 / 7,523 条 / 11.7 MB，`index.json` 7,523 条 / 1.19 MB，7 个合并导入文件已备；小程序详情页确实消费 `lines/memory/scenes/story/tags/level/anim`。
- 未验证：云开发 `cloudEnv` 是否已在真机填入、`fileID` 是否已是真值、7,523 条是否已实际导入云库——本机无云端凭证，只能确认素材齐备，不能确认云端生效。
- 未验证：本轮 `gh api .../pages/deployments` 返回 404，线上 Pages 当前部署的 sha 未复核；不沿用更早快照下结论。远端 main 本轮确认为 `0e8e518`。
- 假设 A1：「935 同等待遇」= 字段齐全 + 逐句 m + 串讲达到 935 首的中位深度（272 字）+ 独立复核 + 进入网页版与云库 + 随版本发布。若枯木只要求「字段齐全、能查到」，工作量降到约 1–2 人日。
- 假设 A2：历史批次吞吐可外推。trans-05 于 2026-10-04 落盘、trans-21 于 2026-10-29 落盘，21 批约覆盖 4,298 行（分母：LEDGER 明列 21 批的句数合计），即约 205 行/批（4,298/21）；按 21 批/4 周折算约 5.25 批/周。这是小 agent 池的历史节奏，不是产能上限，也不是承诺工期。
- 假设 A3：anim 空值是否算缺口取决于仍未拍板的 ADR。按 A（装饰字段、空即终态）计为 0；按 B（去数据化）反而要删字段。这里按 A 计，若枯木改选 B 需重算。

## 4. 三条路线（每条给代价、失败模式、什么时候别用）

### 路线 A：先做「同源一致」，内容深度暂不补

- 做法：提交工作区外国诗改动（需批）→ 推本地两/三笔（需批）→ 网页版 POEMS 换成 7523 首并重建飞花令 → 云库按 7 个合并文件导入、填 `cloudEnv` 与 `fileID` → 三端按同一批抽样 id 对读。
- 代价：工程约 1–2 人日；网页版单文件升到约 13.7 MB，弱网首屏与搜索性能需实测；云端动作只能由人在控制台执行。
- 失败模式：三端口径仍是「字段齐全但串讲短、无逐句译文」，用户若以 935 深度验收会判不合格。
- 什么时候别用：枯木明确要求「同等待遇」按深度而非按字段理解时，别拿路线 A 冒充完成。

### 路线 B：字面兑现「7523 首全部同等待遇」

- 做法：在路线 A 之上，补 40,445 行 m 与 6588 篇串讲，逐批走「生产 → 独立复核 → 合入 → 门闸」；再重跑派生索引、全库 verify、云库重导入、Pages 发布。
- 代价：按 205 行/批，译文约 198 批（40,445/205，向上取整）；按 30 首/批，串讲约 220 批（6,588/30，向上取整）。按历史 21 批/4 周（5.25 批/周）的单池节奏，译文线约 38 周、串讲线约 42 周；两线并行约 10–11 个月，若把产能扩到 4 倍且复核同步扩池，乐观可压到约 3 个月。这不是报价，是按假设 A2 的外推值。
- 失败模式：批量生产最容易出现模板化串讲、人称错乱、引文加错引号、机械判据全绿但语义错；复核产能不足会把门闸变成橡皮图章；13.7 MB 单文件在手机上可能不可用。
- 什么时候别用：如果目标只是「全库可查、重点篇精讲」，不要为了字面平均而把全部 7523 首都做深，优先做高频/精读篇。

### 路线 C：分层待遇（工程全量、内容分层）

- 做法：路线 A 全做；内容上先补 935 首自身的 39 行缺口与外国诗裁定，再按「精读 → 词/曲/赋 → 拓展」优先级逐批补 m 与串讲，每批对外明确标注当前层级。
- 代价：工程同 A；内容可随时停在任何批次，停在哪就是哪一层；需要产品上承认「同等待遇」改为「同字段、分深度」。
- 失败模式：层级标签若不写进 UI 和数据，用户会把短串讲误认为已精讲，形成新的信任问题。
- 什么时候别用：枯木坚持「7523 首逐首同等深度」时，别用 C 交差。

## 4b. 维持现状基线与备选路线

- 不动的代价：网页版停在 935 首、小程序素材停在「已备未导入」、本地两笔继续未推；三端口径分裂会持续产生「到底哪边是真」的重复核对。现状还能撑到下一次有人要求按全库检索或被问到线上版本为止；维持现状本身是合法选项，代价是上述分裂长期存在，不是立刻出错。
- 备选路线：路线 A（同源一致、不补深度）在枯木只要「全库可查」时替代 B；路线 C（分层待遇）在内容产能或复核产能不足时替代 B；什么都不做在本次目标被撤回或降级时替代全部路线。

## 5. 红线与回滚（涉及不可逆动作）

- 本估算没有执行任何 commit、push、云端导入、线上发布或文件覆盖；这些动作按宪法 §9 均需枯木针对本次明确同意。
- 回滚路径：网页版换数组前留当前 `index.html` 的 git blob 与工作区副本，回退即切回 `bf87d13` 版本；云库导入用 Upsert 且先保留旧 `db_import` 快照（现有 `db_import_stale_20261105` 是先例）；本地工作区外国诗改动先 `git diff > 补丁` 再动。
- 失效边界：以上所有首数、行数、字节数只在「网页版工作区 = 4,464,205 字节 / 真值源 = `poems_new.json` 7523 首」这一快照下成立；任何一方合入新内容后需重跑 §6 命令。
