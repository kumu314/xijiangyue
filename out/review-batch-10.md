## 六、小羽提请的两处口径裁决

**Q1「引文处数」：小羽 12 处 vs README 81 处 —— 不是口径差异，是小羽的实现 bug。**
- 实测：**串讲 17 处 + memory 64 处 = 81 处**（与 README 一致）。小羽脚本先 `re.split(标点)` **再**抽 `「([^」]*)」`，**含标点的引文被截断丢弃**（如 `「山空天入海，倚楼望极」` 被 `，` 切成两半、两半都不匹配）；且它**只扫串讲、未扫 memory**（漏 64 处）。这与我方 2026-10-08 记入 skill 的「★ 反向坑：核验别用『标点切段』」同源。
- **裁决**：口径应写死为 ——「**引文处数 = 串讲 + memory_new 中「」配对的总数，抽取时对整段文本 `findall`，禁止先按标点切段**」。我方将把此句补进抽检 skill 的 §C（引文坑）与 SPEC 的抽检口径注。
- **代价与失败模式**：若不写死，每批都会重演「两套实现给出 12 vs 81」并耗费一轮对账；写死的失败模式是「引文含未闭合引号时被漏计」——故同时要求报「引号配对数」作交叉校验（本批 0 异常）。

**Q2「串讲字数下限」：建议改为「均值 ≥270」而非「单篇 ≥250」—— 我不采纳替换，改为并存。**
- 事实：本批 250–274、均值 258.1，**全部合规**（SPEC 单篇 250–480）；历史 batch-08/09 均值约 276。
- **裁决**：**保留 SPEC 硬判据「单篇 250–480」不变**（它可机械二值判定）；把「**目标均值 ≥270**」作为**任务书软目标**下发，**不作 PASS/FAIL 判据**。
- **理由**：均值是统计量，写进 SPEC 会造出新失败模式 —— 30 篇均值 271 但其中 1 篇 249 反而「合规」，或均值 269 而每篇都健康却「不合格」；单篇区间才是二值可判的。小羽的担忧（全批贴下限、易被挑密度）成立，但解法是**任务书加软目标**，不是把硬判据换成统计判据。
- **代价与失败模式**：软目标不具约束力，可能被忽略 → 我在下批任务书里显式写入并请复核时一并报均值。
