## 四、补测：不依赖休眠的延迟差分判据（结果：不可判）

Turso 走 SQL over HTTP（`server.js` 中 `tursoSql → tursoFetch`，**每条语句一次 fetch**）；本地 sqlite 是进程内调用。于是：

- `/api/health` = **0 次**查询
- `/api/me` = **3 次串行**查询（users / progress / checkin，见 `server.js:257-260`）

实测（6 次采样，各取中位）：

```
/api/health 中位 403ms   /api/me 中位 531ms
Δ = 128ms（3 次查询）→ 单次约 43ms
```

**落在「Turso 边缘接入（~40ms）」与「本地库（~0ms）」之间，噪声过大，不足以下结论。**

## 六、方法学沉淀（已写进 `local-html-verify`）

1. **「等待平台休眠」不能作为持久化测试的边界**：免费档休眠时机不可控，且**延迟不是可靠的边界证人**（网络抖动 ±2s，冷启动信号被淹没）。
2. **正确的边界证人**是**服务端自报的启动标识**（boot 时间 / 进程 uptime / 实例 id）——本次发现 `/api/health` 只返回 `ok+time`，无启动标识；`rndr-id` 响应头是**每请求唯一**的请求 id，**不是实例 id**，不能当重启证人。
3. **配对比较优于绝对值**：静默后"背靠背连打 N 次"，用「第 1 次 vs 后续中位」判定冷启动，可抵消跨洋网络漂移。（`restart-witness.mjs`，本轮已在后台运行验证该手段是否可行。）
