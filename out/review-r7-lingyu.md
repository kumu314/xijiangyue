## 4. 发现的问题

### F1【中】测试套件时序不稳：8 次整跑 4 次各挂 1 条，且根因已定位为「等待时间系统性不足」

| 第几次 | 结果 | 挂的是哪条 | 读数 |
|---|---|---|---|
| 1（与小程序检查并行跑） | 84 pass / **1 fail** / 3 skip | `hero 三档截图像素等价` | `maxDelta 3`、差值>1 的像素 366，判据 `maxDelta≤1` |
| 2 | 85 / 0 / 3 | — | — |
| 3 | 84 / **1 fail** / 3 | `打卡后姿态回正（transform 为单位矩阵）` | 第 5 项 `matrix(1.101, 0.0393, -0.0393, 1.101, 0, 0)` |
| 4 | 85 / 0 / 3 | — | — |
| 5 | 85 / 0 / 3 | — | — |
| 6（放行门禁第 1 跑） | 84 / **1 fail** / 3 | `打卡后姿态回正` | 同上 |
| 7（放行门禁第 2 跑） | 84 / **1 fail** / 3 | `打卡后姿态回正` | 同上 |
| 8（放行门禁第 3 跑） | 85 / 0 / 3 | — | — |

**根因不是「随机抖动」，是固定等待时间不够。** 探针 `out/c1-patch/probe_anim.cjs` 点完五项后每 40ms 采样一次 transform，直到五项全为单位矩阵，四次实测回正耗时：

```
945ms / 997ms / 1014ms / 1714ms
```

而 `tests/r7-texture-test.mjs` L786 写的是 `await page.waitForTimeout(760)`。

为什么是 1 秒而不是 `plantBloom .52s`：CSS 是两段串起来的——`.ci-item.fx .ck svg{animation:plantBloom .52s ... both}`（L378，关键帧 58% 处 overshoot 到 `scale(1.1)`，正是失败读数里的 `1.101`），动画结束后 `fx` 类被摘掉、`.ci-item.done .ck svg` 的 `transition` 再把 transform 过渡回单位矩阵。两段相加约 1 秒；机器一忙，摘 `fx` 的那个 `setTimeout` 还会被推迟，实测最慢到 1714ms。

**产品行为本身是对的**：四次探针全部收敛到 `matrix(1,0,0,1,0,0)`，用户看到的是「抽芽 → 回正」的完整动效。**失败的是测量，不是产品。**

**代价**：把它当硬门禁（「0 fail 才许合」），按 8 次里 4 次的实测频率，门禁有一半时间是红的，且红的那次还要人工判真假。
**三种改法各自代价**：

| 改法 | 具体做什么 | 代价 | 会不会动判据 |
|---|---|---|---|
| **甲（推荐）** | 把 L786 的固定 `waitForTimeout(760)` 换成轮询：每 40ms 查五项 transform，全为单位矩阵即继续，超过 3000ms 未收敛则 `SKIP` 并打印实测耗时 | 约 20 行测试代码；判据一个字不改 | **不动**——只是把「等固定时长」换成「等到真的好了」 |
| 乙 | 把 `waitForTimeout` 加到 1800ms | 一行，但按实测最慢 1714ms 仍无余量，机器再忙还会红；且每次跑多等 1 秒 | 不动，但治标不治本 |
| 丙 | 放宽 `hero` 判据的 `maxDelta≤1` 到 `≤2` | 降低拦截强度，需要重新标定「放宽后还拦不拦得住真回归」 | **动判据**，必须单独复核 |

`hero 三档截图像素等价` 是另一条独立的时序问题：`settledShot()` 只校验**同一档位内连拍两枪一致**，没有校验跨档位比对时画面已静止；`maxDelta≤1` 在 390×844、DPR=1 下余量极薄。它 8 次里只红过 1 次，优先级低于上面那条。

### F2【低】执行报告 §0 的读数过期，且头尾自相矛盾

`out/review-r7-execution.md`：

- §0 写「自建断言 **76 条**，带基线整跑 **76 pass / 0 fail / 1 skip**」；实测现在是 **85 条 / 带基线 89 条**。

**放行 `9414210` 推送**，条件两条：

1. **「连跑 3 次 fail=0」这条我实测没达成**——2026-10-28 08:47 起连跑 3 次，结果是 `1 fail` / `1 fail` / `0 fail`，两次红的都是 `打卡后姿态回正`。根因已定位为 L786 的 760ms 固定等待短于实际回正时间（945–1714ms），**产品行为本身正确**（探针四次全收敛）。所以门禁改为：**先按 §4 F1 甲方案把固定等待换成轮询（不动任何判据阈值），改完连跑 3 次 `fail=0` 再推。**

## 9. 失效边界（这份结论在什么情况下不成立）

- **若 `9414210` 之后 `index.html` 或 `tests/r7-texture-test.mjs` 又被改动**，本报告的全部读数作废，需重跑。我复核时的快照是 `origin/main = ba25e32` + 本地 `9414210`。
- **若在别的机器 / 别的 DPR 上跑**，`hero 三档截图` 与 `菊 C 判据（segs=6，门槛 5）` 这两个读数都可能变，因为两者都建立在像素光栅化上，字体与抗锯齿随环境变。
